## Назначение документа

Этот документ описывает модель безопасности LucidSSH простым языком и одновременно задаёт обязательные правила реализации.

Документ предназначен для передачи Claude при:

- доработке технического задания;
- проектировании архитектуры;
- написании и проверке кода;
- подготовке тестов безопасности.

Если требование этого документа конфликтует с удобством реализации, приоритет имеет безопасность. Исключения должны быть отдельно согласованы и документированы.

## 1. Что необходимо защищать

LucidSSH работает с удалёнными серверами, поэтому приложение должно защищать:

- пароли серверов;
- passphrase приватных ключей;
- приватные SSH-ключи;
- команды пользователя и историю команд;
- содержимое терминальной сессии;
- список серверов и их адреса;
- пользователя от подключения к поддельному серверу;
- компьютер пользователя от вредоносного терминального вывода;
- приложение от поддельных обновлений;
- main process от некорректных или вредоносных запросов интерфейса.

## 2. Границы защиты

LucidSSH должен защищать от:

- перехвата SSH-трафика;
- подмены SSH-сервера;
- случайного сохранения секретов в файлах и логах;
- выполнения интерфейсом произвольных операций в Windows;
- вредоносного вывода удалённого сервера;
- случайной отправки многострочных и распознанных опасных команд;
- подмены установщика или обновления;
- известных уязвимостей в устаревших зависимостях.

LucidSSH не может полностью защитить от:

- вредоносной программы, уже работающей от имени пользователя Windows;
- администратора компьютера;
- физического доступа к разблокированному компьютеру;
- действий, которые пользователь осознанно подтвердил;
- всех возможных разрушительных shell-команд.

Интерфейс не должен обещать абсолютную защиту. Например, Страж следует описывать как средство предупреждения о распознанных опасных командах, а не как гарантию блокировки любой опасной операции.

## 3. Архитектура Electron

В Electron-приложении работают отдельные части:

| Часть | Назначение | Уровень доверия |
|---|---|---|
| Renderer | React-интерфейс, xterm.js, формы и панели | Недоверенный |
| Preload | Ограниченный мост между renderer и main | Частично доверенный |
| Main process | SSH, секреты, файлы, SQLite и системные API | Доверенный |
| Удалённый сервер | Отправляет терминальный вывод | Недоверенный |

Renderer необходимо считать потенциально скомпрометированным, потому что он обрабатывает данные удалённого сервера. Он не должен напрямую получать пароли, passphrase, содержимое приватных ключей, доступ к Node.js, файловой системе или объектам SSH-соединения.

## 4. IPC и contextBridge

### Что такое IPC

IPC, Inter-Process Communication, означает обмен данными между процессами. В LucidSSH интерфейс не устанавливает SSH-соединение сам. Он отправляет main process ограниченный запрос, например: `подключить hostId 42`.

Безопасная последовательность:

1. Renderer вызывает разрешённый метод preload.
2. Preload передаёт запрос в main process.
3. Main проверяет запрос.
4. Main выполняет операцию.
5. Renderer получает только необходимый результат.

### Обязательные правила IPC

- IPC доступен только через `contextBridge`.
- Нельзя предоставлять renderer универсальные `send`, `invoke` или имя канала в качестве аргумента.
- Каждый метод должен выполнять одну конкретную операцию.
- Все входящие данные проверяются в main process по схеме: тип, формат, допустимая длина и диапазон.
- `sessionId` проверяется на существование и принадлежность вызвавшему окну.
- `hostId` должен ссылаться на существующую запись, доступную текущему профилю приложения.
- Ошибки, возвращаемые renderer, не должны содержать секреты, пути к чувствительным файлам или внутренний stack trace в production.
- Секреты никогда не возвращаются через IPC.

Пример разрешённого API:

```ts
window.lucidSSH.connectHost(hostId);
window.lucidSSH.disconnectSession(sessionId);
window.lucidSSH.sendTerminalInput(sessionId, text);
window.lucidSSH.confirmHostKey(requestId, decision);
```

Небезопасный API:

```ts
window.electron.invoke(channelName, arbitraryData);
window.files.read(arbitraryPath);
window.shell.execute(arbitraryCommand);
```

## 5. Изоляция renderer

Для каждого `BrowserWindow` обязательны:

```ts
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  sandbox: true,
  preload: preloadPath
}
```

Расшифровка:

- `contextIsolation: true` отделяет страницу интерфейса от привилегированного preload-кода.
- `nodeIntegration: false` запрещает интерфейсу напрямую читать файлы, запускать процессы и использовать Node.js.
- `sandbox: true` дополнительно ограничивает renderer-процесс.
- `preload` открывает только заранее определённый минимальный API.

Также обязательно:

- запретить `webview`;
- запрещать произвольную навигацию окна;
- блокировать `window.open`;
- отключить remote debugging в production;
- не загружать интерфейс или JavaScript с внешних серверов;
- не использовать `eval`, `new Function` и аналогичное исполнение строк как кода.

## 6. CSP

CSP, Content Security Policy, определяет, откуда интерфейс может загружать код и куда может отправлять данные.

Для LucidSSH нужна строгая локальная CSP:

- скрипты только из пакета приложения;
- запрет `unsafe-eval`;
- запрет внешних фреймов;
- запрет загрузки удалённого JavaScript;
- сетевые подключения renderer запрещены, если они не нужны архитектуре;
- внешние изображения и шрифты не загружаются без отдельного решения.

SSH-соединения и проверка обновлений выполняются из main process, а не из renderer.

## 7. SSH и шифрование

SSH создаёт зашифрованный канал между LucidSSH и сервером. Перехвативший сетевой трафик не должен увидеть пароль, команды или ответы сервера.

Обязательные правила:

- использовать SSH-2;
- использовать библиотеку `ssh2` или системный OpenSSH;
- не реализовывать собственную криптографию;
- не включать устаревшие алгоритмы только ради совместимости без отдельного предупреждения;
- проверять host key до аутентификации;
- не выводить секреты и криптографические данные в логи.

## 8. Fingerprint и known_hosts

Fingerprint является коротким отпечатком публичного ключа SSH-сервера. Он подтверждает, что пользователь подключается к тому же серверу, что и раньше.

### Первое подключение

LucidSSH должен:

1. Получить host key сервера.
2. Рассчитать и показать fingerprint, предпочтительно SHA-256.
3. Объяснить пользователю, где его можно проверить.
4. Не продолжать подключение без явного подтверждения.
5. После подтверждения сохранить ключ в локальном `known_hosts`.

### Повторное подключение

- Ключ совпадает: продолжить подключение.
- Сервер ранее неизвестен: запросить подтверждение.
- Ключ изменился: заблокировать подключение до решения пользователя.

При изменении ключа нельзя показывать обычное предупреждение с основной кнопкой `Продолжить`. Нужно объяснить возможную переустановку сервера и риск атаки посредника. Пользователь должен проверить новый fingerprint через независимый источник.

Проверка host key выполняется до отправки пароля или подписи приватным ключом.

## 9. Протокол подключения

Обязательная последовательность подключения:

1. Renderer передаёт в main только `hostId`.
2. Main загружает настройки хоста из SQLite.
3. Main получает пароль или passphrase из Windows Credential Manager, если это требуется.
4. Main открывает соединение с указанным адресом и портом.
5. Main получает и проверяет host key.
6. При новом или изменившемся ключе соединение ожидает решения пользователя.
7. Только после успешной проверки host key выполняется аутентификация.
8. Main создаёт SSH-сессию и возвращает renderer только идентификатор и статус.
9. Секрет удаляется из доступных ссылок сразу после использования и не кэшируется дольше сессии.
10. При отключении уничтожаются ссылки на секреты, потоки и объекты соединения.

Renderer не должен знать пароль, passphrase или содержимое приватного ключа ни на одном этапе.

## 10. Пароли и Windows Credential Manager

Пароли серверов и passphrase ключей хранятся только в Windows Credential Manager через `keytar`.

Запрещено сохранять их:

- в SQLite;
- в `config.json`;
- в `.env` production-сборки;
- в логах;
- в crash reports;
- в истории команд;
- в состоянии renderer;
- в сообщениях IPC.

SQLite хранит только ссылку вида `LucidSSH/{hostId}`. При удалении хоста связанная запись Credential Manager также должна удаляться после подтверждения пользователя.

Поле пароля в UI не должно автоматически заполняться реальным сохранённым значением. Интерфейс показывает только состояние `пароль сохранён`.

## 11. Приватные ключи

LucidSSH хранит путь к оригинальному приватному ключу, но не копирует ключ в свою директорию.

Обязательные правила:

- чтение ключа выполняется только в main process;
- содержимое ключа не передаётся renderer;
- содержимое ключа не сохраняется в SQLite и логах;
- временные незашифрованные копии ключа не создаются;
- passphrase хранится в Credential Manager;
- перед использованием проверяется, что выбран обычный файл допустимого размера;
- ошибки чтения не должны раскрывать содержимое ключа.

Если выполняется конвертация PPK, запрещено оставлять незашифрованный временный ключ. Предпочтительна конвертация в памяти проверенной библиотекой. Если это невозможно, сценарий должен быть отдельно спроектирован и проверен.

## 12. Импорт SSH config и PuTTY

Импортируемые файлы и записи реестра считаются недоверенными данными.

В версии 1.0 из `.ssh/config` разрешено импортировать только:

- `Host`;
- `HostName`;
- `User`;
- `Port`;
- `IdentityFile`;
- `ProxyJump` после отдельной безопасной обработки.

Запрещено автоматически исполнять:

- `ProxyCommand`;
- `LocalCommand`;
- `Match exec`;
- `KnownHostsCommand`;
- произвольные внешние команды и скрипты.

Неподдерживаемые директивы показываются пользователю, но не выполняются.

## 13. Недоверенный терминальный вывод

SSH шифрует канал, но не делает сам сервер доверенным. Сервер управляет данными, поступающими в xterm.js.

Необходимо защититься от:

- управляющих escape-последовательностей;
- OSC 52, способного записывать данные в clipboard;
- вредоносных или маскирующих ссылок;
- бесконечного или чрезмерно большого вывода;
- попыток изменить заголовок окна;
- внедрения HTML или JavaScript через терминальный текст.

Обязательные правила:

- не вставлять terminal output через `innerHTML`;
- отключить OSC 52 по умолчанию;
- не открывать ссылки автоматически;
- перед открытием URL показывать адрес и подтверждение;
- разрешать только явно поддерживаемые протоколы, например `https:` и `http:`;
- запретить `file:`, `javascript:`, `data:` и запуск программ;
- ограничить scrollback и объём буферизуемых данных;
- не допускать блокировки renderer чрезмерным потоком вывода.

## 14. Clipboard и многострочная вставка

При вставке текста из clipboard:

- одна строка вставляется в строку ввода, но проверяется Стражем перед отправкой;
- несколько строк всегда показываются в окне предварительного просмотра;
- найденные опасные строки выделяются;
- пользователь должен явно подтвердить вставку;
- вставка не должна автоматически имитировать Enter без подтверждения;
- пароль и passphrase не должны копироваться приложением в clipboard.

## 15. Страж опасных команд

Страж работает в main process до отправки команды по SSH.

Проверке подлежат команды из всех источников:

- ручной ввод;
- clipboard;
- история;
- каталог команд;
- breadcrumb;
- будущие сниппеты.

Паттерны хранятся отдельно в `src/main/guard/patterns.ts` и покрываются тестами.

Для подтверждения опасной команды недостаточно кнопки `ОК`. Пользователь вводит имя затрагиваемого объекта или другой контекстный текст. Результат сохраняется в истории как `заблокировано` или `подтверждено`.

Страж не является sandbox и не способен распознать все эквивалентные способы разрушительного действия. Это ограничение должно быть явно отражено в документации и интерфейсе.

## 16. История команд

История может случайно содержать токены и пароли, например:

```bash
export API_KEY=secret
curl -H "Authorization: Bearer secret" example.com
mysql --password=secret
```

Требования:

- детектировать распространённые способы передачи секретов;
- маскировать значение секрета перед записью;
- позволять не сохранять отдельную команду;
- позволять отключить историю глобально или для хоста;
- не сохранять terminal output по умолчанию;
- позволять удалить отдельную запись и очистить историю;
- не показывать замаскированный секрет через поиск или экспорт;
- ограничить доступ к SQLite-файлу текущим пользователем Windows.

Автоматическое удаление старых записей по лимиту не заменяет ручную очистку и маскирование секретов.

## 17. Логи и диагностика

Production-логи не должны содержать:

- пароли и passphrase;
- содержимое приватных ключей;
- секреты из команд;
- полный terminal output;
- содержимое clipboard;
- необработанные IPC-объекты;
- данные Credential Manager.

Вместо секретных значений используются внутренние ID и безопасные категории ошибок.

Безопасно:

```text
SSH authentication failed: hostId=42, method=publickey
```

Небезопасно:

```text
Authentication failed: host=server.example password=qwerty123
```

Отладочное логирование чувствительных данных не должно включаться в production-сборке.

## 18. Локальные файлы и SQLite

Хранилища LucidSSH:

| Данные | Хранилище |
|---|---|
| Хосты и группы | SQLite |
| История | SQLite |
| Пароли и passphrase | Windows Credential Manager |
| Known hosts | Локальный файл OpenSSH-формата |
| Настройки | JSON без секретов |

Требования:

- файлы создаются с доступом только для текущего пользователя, насколько это поддерживает Windows;
- SQL-запросы параметризуются;
- значения не объединяются с SQL строковой конкатенацией;
- входные данные имеют ограничения длины;
- повреждённая БД не должна приводить к выполнению кода;
- резервные копии и экспорт не должны незаметно включать секреты.

Полное шифрование SQLite не защищает от вредоносной программы, запущенной от имени пользователя, и не заменяет правильное хранение секретов.

## 19. Shell integration, breadcrumb и dashboard

Shell integration и dashboard отправляют команды на сервер, поэтому их строки должны быть статическими и контролироваться приложением.

Запрещено:

- подставлять имя хоста, путь или другой недоверенный текст в shell-команду без безопасного экранирования;
- исполнять текст, присланный сервером как служебное сообщение, без строгого формата;
- смешивать служебные маркеры shell integration с обычным выводом без проверки.

Dashboard использует отдельный SSH exec-канал и заранее определённый набор команд. Значения метрик парсятся как данные и не исполняются.

### 19.1 Поддержка shell'ов

Маркер breadcrumb/истории (`__lucidssh_mark`) перепривязывается перед каждым приглашением: `precmd`-хук для zsh, встраивание в `PS1` для остальных (POSIX-совместимо — переразворачивается при каждом показе приглашения).

Подтверждено на реальных серверах (09.07.2026):
- **bash** — работает (`PS1`).
- **zsh** — работает (`precmd`-хук).
- **ash / BusyBox** (в т.ч. на роутерах — Keenetic и подобные) — работает через `PS1` с 09.07.2026; до этого `PROMPT_COMMAND` (bash-специфика) на ash не срабатывал вовсе, маркер приходил один раз при подключении, breadcrumb и история молча не обновлялись.

Не проверено и вероятно не заработает без отдельной доработки: **fish**, **csh/tcsh** — не-POSIX синтаксис, `PS1`/`PROMPT_COMMAND`/`precmd` там не работают в этом виде. Деградация ожидается тихой (сама SSH-сессия и терминал работают нормально, просто breadcrumb/история/детектор ошибок не активируются) — это не проверялось на реальном сервере, только предположение из архитектуры. Если понадобится поддержка — отдельная ветка в setup-скрипте по аналогии с zsh-веткой.

## 20. Обновления и подпись

Обновление должно проходить несколько проверок:

- загрузка только по HTTPS с заранее заданного домена;
- цифровая подпись установочного пакета;
- проверка ожидаемого издателя;
- отклонение изменённого или неподписанного пакета;
- защита от установки более старой уязвимой версии;
- атомарная установка с безопасным восстановлением после ошибки.

HTTPS защищает загрузку в сети, а цифровая подпись подтверждает происхождение и целостность файла. Нужны оба механизма.

Проверка обновлений является отдельным разрешённым сетевым соединением. Поэтому требование `никакого внешнего трафика` следует формулировать так: приложение создаёт только SSH-соединения, явно инициированную проверку обновлений на заданном домене и иные отдельно документированные соединения.

## 21. Зависимости и сборка

Требования к цепочке поставки:

- хранить lock-файл зависимостей в репозитории;
- использовать воспроизводимую установку зависимостей;
- регулярно проверять известные уязвимости;
- своевременно обновлять Electron, `ssh2`, xterm.js и native-модули;
- минимизировать количество зависимостей;
- не загружать исполняемый код во время работы приложения;
- хранить сертификат подписи и его пароль вне репозитория;
- не публиковать секреты в CI-логах и артефактах;
- подписывать production-сборки и установщик.

## 22. Внешние ссылки

Любая ссылка из терминала, базы ошибок, каталога команд или интерфейса считается недоверенной до проверки.

Перед открытием необходимо:

1. Разобрать URL стандартным парсером.
2. Проверить разрешённый протокол.
3. Показать пользователю реальный адрес.
4. Открыть его системным браузером только после допустимого действия пользователя.

Запрещено открывать ссылки внутри привилегированного окна Electron.

## 23. Автоматические отчёты и телеметрия

В версии 1.0 отсутствуют:

- телеметрия;
- автоматическая отправка crash reports;
- аналитика использования;
- отправка команд или terminal output;
- облачная синхронизация.

Даже обезличенная отправка данных не добавляется без отдельного решения, описания состава данных и явного согласия пользователя.

## 24. Минимальные проверки безопасности

Перед выпуском необходимо проверить:

- пароль отсутствует в SQLite, JSON, логах и crash-данных;
- приватные ключи не копируются в директорию приложения;
- изменившийся fingerprint блокирует подключение;
- аутентификация не начинается до проверки host key;
- renderer не имеет доступа к Node.js и файловой системе;
- IPC не содержит универсальных каналов и проверяет аргументы;
- секреты не возвращаются в renderer;
- OSC 52 отключён по умолчанию;
- опасные URL-схемы блокируются;
- многострочная вставка требует подтверждения;
- команды с типичными токенами маскируются в истории;
- `ProxyCommand`, `LocalCommand` и `Match exec` не исполняются при импорте;
- поддельное обновление отклоняется;
- production-сборка подписана;
- зависимости проверены на критические известные уязвимости.

## 25. Правило для Claude при написании кода

При реализации любого модуля Claude должен:

1. Определить, какие недоверенные данные входят в модуль.
2. Определить, содержит ли модуль секреты.
3. Выполнять привилегированные операции только в main process.
4. Добавлять узкий типизированный IPC-контракт, если нужен доступ из renderer.
5. Валидировать данные в main process независимо от проверок UI.
6. Не записывать секреты в логи и ошибки.
7. Добавлять негативные тесты: некорректные типы, слишком длинные строки, неизвестные ID и запрещённые значения.
8. Проверять, что изменение не расширяет сетевой доступ приложения без документированного решения.
9. Не ослаблять существующие настройки Electron ради удобства разработки.
10. Явно сообщать, если требование невозможно выполнить безопасно в выбранной архитектуре.

## 26. Ключевой принцип

LucidSSH использует многоуровневую защиту:

1. SSH шифрует соединение.
2. Fingerprint подтверждает сервер.
3. Credential Manager защищает пароли.
4. Main process изолирует секреты и системные операции.
5. IPC разрешает только конкретные действия.
6. Renderer не имеет прямого доступа к Windows и Node.js.
7. Терминальный вывод считается недоверенным.
8. История очищается от вероятных секретов.
9. Страж снижает риск ошибки пользователя.
10. Подпись защищает обновления.
11. Аудит зависимостей закрывает известные уязвимости.

Отказ одного слоя не должен автоматически давать доступ ко всем остальным частям приложения.
