# Jump-хост: только один прыжок, обеспечивается фильтрацией списка выбора

Решение (сессия `/grill-with-docs` по фидбеку «не хватило поддержки jump-хоста», 2026-07-31): `proxyJump` хоста хранит ссылку (`hostId`) на другой сохранённый хост, а не свободную строку адреса. Выбор bastion-хоста происходит через search-комбобокс (переиспользует HM-05), список кандидатов в котором **отфильтрован до хостов, у которых нет собственного `proxyJump`**, плюс исключён сам редактируемый хост.

Этот фильтр — не просто UX-удобство, а единственный механизм, которым ограничен scope до single-hop. В «настоящем» OpenSSH `ProxyJump` поддерживает цепочку через запятую (`bastion1,bastion2,...`); мы такие цепочки не поддерживаем. Раз кандидат в bastion по построению списка не может сам иметь `proxyJump`, дальше одного прыжка уйти невозможно ни при каком вводе пользователя — отдельная проверка на циклы/глубину цепочки в момент подключения не нужна.

**Почему не общая проверка на циклы в момент подключения:** тогда пришлось бы держать логику обхода графа ссылок (A→B→C→...) при каждой попытке соединения и понятно объяснять пользователю ошибку "обнаружен цикл" — сложнее и менее предсказуемо, чем просто не дать создать такую конфигурацию через UI.

**Почему не поддержали multi-hop цепочки:** аудитория 1.0 — новички и домашняя лаборатория (§1.3 ТЗ), не сложные корпоративные сети с несколькими периметрами; та же логика, что и по OQ-07 (SOCKS5/HTTP-прокси отложены в `Development_Roadmap.md` §3.14). Исходная формулировка `SSH-05` в ТЗ — «Jump host (ProxyJump)» в единственном числе.

Если multi-hop понадобится позже — это отдельная фича с явным обходом графа (или явным списком нескольких хопов в форме хоста), не расширение текущего фильтра.

Решение принято 2026-07-31.
