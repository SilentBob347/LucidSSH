# Jump-хост: только один прыжок

Решение (сессия `/grill-with-docs` по фидбеку «не хватило поддержки jump-хоста», 2026-07-31): `proxyJump` хоста хранит ссылку (`hostId`) на другой сохранённый хост, а не свободную строку адреса. Выбор bastion-хоста происходит через search-комбобокс (переиспользует HM-05), список кандидатов в котором **отфильтрован до хостов, у которых нет собственного `proxyJumpHostId`**, плюс исключён сам редактируемый хост.

В «настоящем» OpenSSH `ProxyJump` поддерживает цепочку через запятую (`bastion1,bastion2,...`); мы такие цепочки не поддерживаем — single-hop и только single-hop.

**Обновление 2026-08-04 (code-review):** первая версия этого ADR утверждала, что фильтра списка в форме достаточно как «единственного механизма» — это оказалось неверно. Фильтр закрывает только одно направление (нельзя выбрать bastion, у которого уже есть свой jump), но не другое (ничто не мешало назначить jump-хост тому, кто сам уже используется как чей-то bastion — цепочка A→B→C собиралась именно с этой, необработанной стороны). Фильтр также не защищал прямой вызов IPC-канала и не касался импорта (`~/.ssh/config`, JSON) и миграции старых данных — все эти пути резолвили связь по имени, не проверяя, не создаёт ли она второй прыжок.

Инвариант перенесён туда, где он не обходится: `hosts/repository.ts` → `checkJumpHost(jumpHostId, hostId?)` — единственное место, которое решает, можно ли принять связку «хост → jump-хост» (проверяет обе стороны: у кандидата нет своего jump, и сам хост не используется как чей-то jump). IPC-хендлеры `hosts:create`/`hosts:update` зовут его перед записью; оба импорта и миграция v2 — тоже, каждый на своих данных (миграция — раз БД в процессе апгрейда, `checkJumpHost` там ещё недоступен, — на разрешённом графе рёбер: выживает только ребро, чья цель никуда не ходит). Фильтр списка в форме остался, но теперь это первая линия/UX-подсказка, не гарантия; для хоста, который сам уже кем-то используется как bastion, поле в форме дополнительно блокируется целиком с объяснением. Дальше одного прыжка уйти по-прежнему невозможно ни при каком вводе — просто гарантия живёт в одном месте на стороне данных, а не размазана по фильтру.

**Почему не общая проверка на циклы в момент подключения:** тогда пришлось бы держать логику обхода графа ссылок (A→B→C→...) при каждой попытке соединения и понятно объяснять пользователю ошибку "обнаружен цикл" — сложнее и менее предсказуемо, чем не дать создать такую конфигурацию при сохранении хоста.

**Почему не поддержали multi-hop цепочки:** аудитория 1.0 — новички и домашняя лаборатория (§1.3 ТЗ), не сложные корпоративные сети с несколькими периметрами; та же логика, что и по OQ-07 (SOCKS5/HTTP-прокси отложены в `Development_Roadmap.md` §3.14). Исходная формулировка `SSH-05` в ТЗ — «Jump host (ProxyJump)» в единственном числе.

Если multi-hop понадобится позже — это отдельная фича с явным обходом графа (или явным списком нескольких хопов в форме хоста), не расширение текущей проверки.

Решение принято 2026-07-31, уточнено 2026-08-04.
