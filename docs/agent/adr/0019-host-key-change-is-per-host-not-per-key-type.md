# Смена ключа хоста определяется по адресу:порту, а не по типу ключа

Решение (сессия `/grill-with-docs` по тикету
`.scratch/security-scan-2026-10/issues/03-host-key-change-across-key-types.md`,
2026-10-14): «известен / изменён / первое подключение» решается для пары
адрес:порт целиком.

- Предъявленный ключ совпал с **любым** доверенным ключом адреса:порта — известен.
- У адреса:порта нет ни одного доверенного ключа — первое подключение (SSH-03).
- Доверенные ключи есть, ни один не совпал — **смена** (SSH-04), какого бы типа ни
  был предъявленный ключ. Полный сценарий: модалка «изменён», «Продолжить» по
  умолчанию недоступно, событие NOTIF-03.
- Accept в сценарии смены удаляет **все** записи адреса:порта и пишет один новый
  ключ. У хоста один доверенный ключ.
- Если у адреса:порта есть доверенные ключи, их алгоритмы ставятся **первыми** в
  `algorithms.serverHostKey`; остальные алгоритмы не исключаются. Технически это
  `{ remove: X, prepend: X }`: ssh2 в `prepend` пропускает алгоритм, который уже
  есть в списке по умолчанию, так что один `prepend` порядок не меняет.
- Модалка смены подписывает тип у текущего и у каждого прежнего отпечатка и
  показывает все прежние ключи — те, что accept удалит.

Термины — [CONTEXT.md](../CONTEXT.md), раздел «Доверие ключу хоста».

**Почему это вообще решение, а не очевидность.** До него `findKnownKey` искал ключ
по (адрес, порт, тип), а `replaceKnownKey` заменял ключ того же типа. Подменный
сервер, предъявивший ключ типа, ещё не сохранённого для хоста, получал модалку
**первого подключения** — мягкую, с зелёным отпечатком, — и после «Принять» его
ключ дописывался рядом с настоящим. Дальше подмену не подсвечивало уже ничего.
SSH-04 при этом формально выполнялось: «изменение fingerprint» молча читалось как
«изменение fingerprint этого типа». Найдено сканом claude-security (`b8aa6ab`,
находка F15, все 8 прогонов).

**Мы строже OpenSSH — намеренно.** OpenSSH на ключ другого типа для известного
хоста показывает обычный промпт нового хоста с дополнительным предупреждением
«для этого хоста известны ключи другого типа» (`show_other_keys`), а не аварийное
«REMOTE HOST IDENTIFICATION HAS CHANGED». Мы показываем полный SSH-04. Обоснование:
при предпочтении сохранённых алгоритмов (ниже) до этой ветки доходит только сервер,
у которого не осталось **ни одного** ранее доверенного типа — честно это случается
редко (админ убрал тип из `sshd_config`), а аудитория продукта — новички, которым
нужна громкая тревога, а не тонкое различие между двумя видами предупреждения.

**Рассмотренные альтернативы:**

- **Исключающее закрепление алгоритмов** (предлагать серверу только сохранённые
  типы) — отклонено. Сервер без сохранённого типа роняет handshake с «нет общего
  алгоритма»: вместо модалки пользователь видит ошибку соединения, а выход — только
  удалить запись в «Настройки → Безопасность» (SET-04). Ветка смены становится
  недостижимой, решение пользователя подменяется тупиком. Рекомендация скана
  («закрепить, как OpenSSH») неточна: OpenSSH алгоритмы упорядочивает, а не исключает.
- **Не трогать алгоритмы** — отклонено. Без предпочтения сервер, у которого просто
  появился новый тип (и он стоит выше в списке ssh2 по умолчанию), поднимал бы
  тревогу смены на каждом подключении. Ложная тревога для новичка хуже отсутствующей:
  её учатся прокликивать.
- **Третья модалка в стиле OpenSSH** («ключи другого типа уже доверены») — отклонено.
  Новый вид модалки, новые i18n-ключи и отдельное решение про NOTIF-03 ради ветки,
  которая при предпочтении алгоритмов почти всегда означает подмену.
- **Accept в сценарии смены добавляет ключ рядом** — отклонено. Это ровно та дыра,
  которую закрываем: ошибочно принятый подменный ключ остаётся доверенным навсегда.
- **Accept заменяет только ключ того же типа (как было)** — отклонено: при смене
  типа удалять нечего, и замена вырождается в добавление рядом.
- **Показывать один прежний отпечаток** — отклонено. Accept удаляет все прежние
  ключи; пользователь должен видеть, что перестаёт быть доверенным.

**Принятая цена.**

- Честный сервер, убравший все ранее доверенные типы, получает тревогу смены. Это
  ожидаемо: со стороны клиента он неотличим от подмены.
- Строка `known_hosts` с несколькими хостами через запятую удаляется при accept
  целиком — вместе с доверием для соседних хостов строки. Так вёл себя и прежний
  `replaceKnownKey`; сами мы такие строки не пишем, они возможны только после
  ручной правки файла.
- Уже накопленные записи с несколькими ключами на хост (оставленные прежним
  поведением) не мигрируются: они остаются доверенными, совпадение с любым из них —
  совпадение, и схлопываются в одну при первой же принятой смене.

**Границы, которые легко принять за недоделку:**

- **Модалка первого подключения тип ключа не показывает.** Подпись типа добавлена
  только в модалку смены, где без неё два отпечатка разных типов выглядят как
  ротация ключа одного типа.
- **`hostkeys-00@openssh.com` (UpdateHostKeys) не поддерживается.** Узнавать новые
  типы ключей от уже аутентифицированного сервера — отдельная функция, не часть
  этого решения.
